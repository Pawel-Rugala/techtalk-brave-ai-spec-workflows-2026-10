01 · Kod jest tani

Co potaniało, a co nie?

TANIE

Produkcja kodu

  • pisanie implementacji
  • boilerplate, CRUD, migracje
  • refaktor i przepisywanie
  • prototyp w godzinę
DROGIE — JAK ZAWSZE

Wszystko wokół

  • złe zrozumienie problemu
  • pominięte reguły i edge case'y
  • zła architektura
  • brak sposobu, by sprawdzić, że działa

Potaniało pisanie.
Myślenie i sprawdzanie — nie.

[3:30–4:30] Lewa strona: to, co AI robi świetnie i tanio. Prawa: to, co kosztowało nas zawsze najwięcej — źle zrozumiany problem, brakująca reguła, zła architektura, brak testów. AI tego nie potaniło. Wręcz przeciwnie: błąd w zrozumieniu problemu agent zaimplementuje szybko i pewnie siebie. Skoro pisanie jest tanie, to wartość developera musi być gdzie indziej.
01 · Kod jest tani

Nowy developer: dwa mięśnie

PRZED KODEM

Biznes & domena

  • rozumie, po co powstaje feature
  • rozmawia z biznesem, nie z ticketem
  • zamienia „mniej więcej” w reguły
  • ma zdanie o produkcie
PO KODZIE

Weryfikacja

  • definiuje, co znaczy „działa”
  • projektuje testy i bramki
  • czyta kod krytycznie, nie „na oko”
  • nie ufa "Looks good ✅"

Kod pisze agent. Ty odpowiadasz za to, CO powstaje i CZY działa.

[4:30–6:00] To jest teza całej prezentacji. Developer nie jest już operatorem klawiatury. Potrzebuje dwóch mięśni. Pierwszy — biznes i domena: rozumiesz, po co to budujemy, potrafisz z niejasnego „user ma móc zapłacić” wyciągnąć konkretne reguły. Drugi — weryfikacja: wiesz, co znaczy „działa”, i potrafisz to sprawdzić systemowo, a nie wzrokiem. Środek — samo pisanie kodu — przejmuje agent.

02 · Spec-driven development

Przykład: POST /payments

JIRA · PAY-123

Add endpoint allowing a user to pay an invoice.

Priority: High · Estimate: 1 SP 🙂

agent · payments.ts// 🤖 agent: "Done! Endpoint ready ✅" router.post('/payments', async (req, res) => { const invoice = await db.invoices.find(req.body.invoiceId); const payment = await db.payments.create({ invoiceId: invoice.id, amount: req.body.amount, }); res.status(201).json(payment); });
no idempotency key concurrent payments? invoice already paid? no event emitted what if it fails?

Kod jest sensowny. Problem w tym, że nikt nie wie, czy jest poprawny.

[7:30–9:00] Nasz przykład na całą resztę prezentacji — PAY-123. Typowy ticket, agent coś generuje, wygląda OK. Stemple wpadają: brak klucza idempotencji (retry = podwójna płatność), dwie równoległe płatności, już opłacona faktura, brak eventu PaymentCreated, co gdy coś się wywali w połowie. Agent nie zgadł, bo NIKT mu nie powiedział. To nie jest problem modelu — to problem wejścia.
02 · Spec-driven development
specs/PAY-123-create-payment.md# Create Payment ## Goal User pays an open invoice, fully or partially. ## API POST /payments { invoiceId, amount, clientRequestId } ## Rules - invoice exists and status = OPEN✓ already paid - amount ≤ invoice.remainingAmount - idempotent by clientRequestId✓ idempotency - optimistic lock on invoice✓ concurrency ## Events PaymentCreated · PaymentFailed✓ event ## Errors 404 · 409 ALREADY_PAID · 422 · retry only 5xx✓ failures ## Acceptance - [ ] same clientRequestId → same payment - [ ] 2 parallel payments → exactly 1 succeeds

Co to jest spec?

Spec ≠ 40-stronicowy Word

Markdown w repo. Na tyle konkretny, żeby inny developer albo agent zrobił feature bez zadawania 20 pytań.

AI nie potrzebuje lepszych promptów.
Potrzebuje mniej zgadywania.

[9:00–11:00] To samo PAY-123, ale ze specem. Zielone znaczniki: każdy stempel z poprzedniego slajdu jest teraz zamknięty jedną linijką. Opłacona faktura → status OPEN. Retry → clientRequestId. Równoległe płatności → optimistic lock. Event → PaymentCreated. Błędy → lista kodów i co retryować. Spec to nie 40 stron w Wordzie. To markdown w repo, obok kodu, review jak kod. Test: czy inny developer albo agent zrobi to bez 20 pytań? Każda luka w specu to miejsce, w którym agent zgaduje — i zgaduje pewnie siebie.

Czego brakuje?

„A jeśli faktura jest już opłacona?”

↓ spec.md — w repo, review jak kod

Narzędzia: GitHub Spec Kit · Kiro · BMAD · własne komendy i skille — wybór narzędzia jest wtórny.

[11:00–12:30] Tu widać przesunięcie w stronę biznesu. Spec nie spada z nieba i nie pisze go PO sam. Biznes mówi, PO CO. Developer zamienia to w reguły — tu jest jego nowa wartość. A agent jest świetny w zadawaniu niewygodnych pytań: zamiast kazać mu zgadywać, każ mu najpierw wypisać wszystko, czego nie wie. To odwraca proces: agent nie zgaduje — agent pyta. Narzędzia: Spec Kit, Kiro, BMAD albo własne komendy. Narzędzie jest wtórne, nawyk jest kluczowy.

[12:30–14:00] Tak wygląda spec-driven workflow. Dwie bramki, gdzie decyduje człowiek. Pierwsza: SPEC. Zanim powstanie linijka kodu, człowiek zatwierdza, CO budujemy. Błąd złapany tu kosztuje minuty, a nie dni. Druga: PR. Człowiek decyduje, czy to wchodzi. Pomiędzy: build loop. Agent planuje, koduje, pisze testy, robi review, poprawia — aż spec jest spełniony. Spec to szyna: z tego samego pliku powstają kod, testy (z acceptance criteria), review i scenariusze QA. To nie „więcej dokumentacji” — to input do maszyny.
02 · Spec-driven development

Kiedy SDD boli

Spec-waterfall

Tydzień pisania specu, zanim ktokolwiek zobaczy działający kod.

Mały spec per feature, iteracyjnie. Prototyp też może być inputem.

Spec drift

Kod się zmienia, spec nie. Po miesiącu spec kłamie.

Zmiana specu w tym samym PR co kod. Review sprawdza oba.

Spec na wszystko

Spec dla literówki w labelu. Ceremonia zamiast wartości.

Spec tam, gdzie są reguły biznesowe albo ryzyko.

Tyle specu, ile ryzyka.

[14:00–15:30] Żeby nie brzmiało jak religia. Słyszę trzy zarzuty i są zasadne. „To waterfall od nowa” — tak, jeśli piszesz 40 stron na start. Mały spec, iteracyjnie. „Spec się rozjedzie z kodem” — tak, jeśli żyje poza PR-em. Spec zmieniamy w tym samym PR co kod. „Spec do każdej zmiany?” — nie. Literówka nie potrzebuje specu, płatności potrzebują. Zasada: tyle specu, ile ryzyka. To zamyka część drugą — teraz: co jeśli takich PAY-123 mamy pięćdziesiąt naraz?

Od assistant do factory

LVL 1

AI Assistant

LVL 2

AI Agent

Spec → Agent ├─ reads repository ├─ changes code ├─ runs tests ├─ fixes errors └─ creates PR

Developer deleguje całe zadanie.

LVL 3

AI Factory

N × ticket → Spec Agent → Architect Agent → BE ∥ FE Agents → Testing Agent → Review Agent → Human gate

Developer projektuje system, który dostarcza.

[15:30–16:30] Trzy poziomy. 1: asystent — prowadzisz każdy krok, AI podpowiada. 2: agent — dajesz mu spec i delegujesz całe zadanie. Tu jest dziś większość z nas, którzy używają Claude Code, Codexa czy Cursora w trybie agenta. 3: fabryka — wiele ticketów naraz, wyspecjalizowane agenty, separacja odpowiedzialności, bramki. Nie projektujesz już kodu — projektujesz system, który produkuje kod. Zobaczmy, jak przez taki system przechodzi PAY-123.

AI FACTORY

▶ PAY-123

AI Factory = workflow, nie model.

Modele będą się zmieniać. Workflow jest twoją przewagą.

[16:30–18:30] Animacja leci sama (~20 s). Komentuj na bieżąco: ticket wpada, Spec Agent robi z niego spec (to, co widzieliśmy przed chwilą), Architect decyduje o kontraktach, BE i FE implementują równolegle. Testing Agent — tu łapiemy buga i go wyrzucamy, bo test wynika ze specu, a nie z kodu. Review względem specu, PR, człowiek zatwierdza. Na końcu: AI Factory = workflow, nie model. Claude, Codex, Gemini — modele się zmieniają. Workflow zostaje.
03 · AI Factory

Co się zmienia przy skali?

01

Wąskim gardłem jest człowiek

Agenci produkują więcej PR-ów, niż zespół jest w stanie przeczytać. Limitem są spec i review — nie kod.

02

Separacja ról

Kto implementuje, ten nie reviewuje. Osobny agent, osobny kontekst — review względem specu, nie własnych założeń.

03

Fabryka to też kod

Prompty, skille, CLAUDE.md, checklisty — w repo, wersjonowane, z review. Naprawiasz fabrykę, nie każdy PR.

04

Mierzysz linię produkcyjną

% PR-ów bez poprawek · rework · bugi na produkcji · czas ticket → merge · koszt feature'a.

[18:30–20:30] Cztery rzeczy, których nie widać na poziomie jednego agenta. 01: kod przestaje być limitem. Limitem jest to, ile specu zespół zatwierdzi i ile PR-ów przeczyta. Dlatego bramki muszą być mniej liczne, ale mocniejsze. 02: jeden gigantyczny agent, który pisze i sam siebie reviewuje, zawsze powie „looks good”. Rozdziel role i konteksty. 03: kiedy agent robi ten sam błąd po raz trzeci, nie poprawiasz PR-a — poprawiasz fabrykę: skill, regułę, checklistę. 04: fabrykę się mierzy jak linię produkcyjną. Jeśli nie wiesz, ile PR-ów wraca do poprawek, nie wiesz, czy fabryka działa. [Tu najlepiej pasuje twój własny przykład / liczby z projektu.]

Najważniejsze zdanie: nie ufamy agentowi, ufamy systemowi weryfikacji wokół agenta.
