02 · Spec-driven development

Przykład: POST /payments

JIRA · PAY-123

Add endpoint allowing a user to pay an invoice.

Priority: High · Estimate: 1 SP 🙂

agent · payments.ts// 🤖 agent: "Done! Endpoint ready ✅" router.post('/payments', async (req, res) => { const invoice = await db.invoices.find(req.body.invoiceId); const payment = await db.payments.create({ invoiceId: invoice.id, amount: req.body.amount, }); res.status(201).json(payment); });
no idempotency key concurrent payments? invoice already paid? no event emitted what if it fails?

Kod jest sensowny. Problem w tym, że nikt nie wie, czy jest poprawny.

[7:00–9:00] Nasz przykład na całą prezentację. Typowy ticket, agent coś generuje — wygląda OK. Stemple wpadają jeden po drugim: brak klucza idempotencji (retry = podwójna płatność), co przy dwóch równoległych płatnościach, co z już opłaconą fakturą, brak eventu PaymentCreated, co gdy coś się wywali w połowie. Agent nie zgadł, bo NIKT mu nie powiedział. To nie jest problem modelu.
02 · Spec-driven development

Co to właściwie jest spec?

Spec ≠ 40-stronicowy Word

Spec jest wystarczająco konkretny, żeby inny developer albo agent zaimplementował feature bez zadawania 20 pytań.

specs/create-payment.md# Create Payment ## Goal User can create a payment for an existing invoice. ## API POST /payments { invoiceId, amount, clientRequestId } ## Business rules - invoice must exist - invoice cannot already be paid - amount must equal outstanding balance - operation must be idempotent ## Events PaymentCreated · PaymentFailed ## Error cases 404 INVOICE_NOT_FOUND · 409 PAYMENT_ALREADY_EXISTS ## Acceptance criteria - [ ] duplicate clientRequestId → same payment
[9:00–11:00] Od razu zaznacz: spec to NIE 40 stron w Wordzie. To markdown w repo, obok kodu. Test: czy inny developer albo agent zaimplementuje to bez zadawania 20 pytań? Pokaż sekcje: goal, API, reguły biznesowe, eventy, błędy, acceptance criteria.
02 · Spec-driven development

Dobry spec vs zły prompt

PROMPT

Add payment endpoint.

…i agent zgaduje resztę.

SPEC
POST /payments
Preconditions: invoice exists · status = OPEN
Invariant: payment.amount ≤ invoice.remainingAmount
Idempotency: clientRequestId
Concurrency: optimistic lock on invoice
Side effects: PaymentCreated event
Failure modes: 404 · 409 · 422 → retry only 5xx

AI nie potrzebuje bardziej kreatywnych promptów.
AI potrzebuje mniej zgadywania.

[11:00–12:30] Lewa strona — to, co dziś wrzucamy agentowi. Prawa — to samo, ale bez niedomówień. Każdy wiersz spec zamyka jeden stempel z poprzedniego przykładu. Puenta: nie potrzebujemy lepszych promptów, potrzebujemy mniej zgadywania. Każda luka w specu to miejsce, w którym agent zgaduje — i zgaduje pewnie siebie.

[14:00–15:30] Tak wygląda spec-driven workflow. Problem → spec → plan → agenci → review → PR. Ważne są dwie bramki, gdzie decyduje człowiek. Pierwsza: SPEC. Zanim powstanie jakakolwiek linijka kodu, człowiek zatwierdza, CO budujemy. Błąd złapany tu kosztuje minuty, a nie dni. Druga: PR. Na końcu człowiek decyduje, czy to wchodzi. Pomiędzy bramkami jest build loop: agent sam robi plan, rozbija go na taski, koduje, pisze testy, robi review i poprawia — w pętli, aż spec jest spełniony. Nikt nie prowadzi go za rękę krok po kroku. Spec to szyna, po której jedzie cały proces — pętla sprawdza się względem specu, nie względem własnego zdania. ▸ Człowiek nie wykonuje każdego kroku. Człowiek pilnuje bramek. To prowadzi prosto do AI Factory.
02 · Spec-driven development

Kiedy SDD boli

Spec-waterfall

Tydzień pisania specu, zanim ktokolwiek zobaczy działający kod.

Mały spec per feature, iteracyjnie. Prototyp też może być inputem.

Spec drift

Kod się zmienia, spec nie. Po miesiącu spec kłamie.

Zmiana specu w tym samym PR co kod. Review sprawdza oba.

Spec na wszystko

Spec dla literówki w labelu. Ceremonia zamiast wartości.

Spec tam, gdzie są reguły biznesowe albo ryzyko.

Tyle specu, ile ryzyka.

[14:00–15:30] Żeby nie brzmiało jak religia. Słyszę trzy zarzuty i są zasadne. „To waterfall od nowa” — tak, jeśli piszesz 40 stron na start. Mały spec, iteracyjnie. „Spec się rozjedzie z kodem” — tak, jeśli żyje poza PR-em. Spec zmieniamy w tym samym PR co kod. „Spec do każdej zmiany?” — nie. Literówka nie potrzebuje specu, płatności potrzebują. Zasada: tyle specu, ile ryzyka. To zamyka część drugą — teraz: co jeśli takich PAY-123 mamy pięćdziesiąt naraz?

03 · AI Factory

Co się zmienia przy skali?

01

Wąskim gardłem jest człowiek

Agenci produkują więcej PR-ów, niż zespół jest w stanie przeczytać. Limitem są spec i review — nie kod.

02

Separacja ról

Kto implementuje, ten nie reviewuje. Osobny agent, osobny kontekst — review względem specu, nie własnych założeń.

03

Fabryka to też kod

Prompty, skille, CLAUDE.md, checklisty — w repo, wersjonowane, z review. Naprawiasz fabrykę, nie każdy PR.

04

Mierzysz linię produkcyjną

% PR-ów bez poprawek · rework · bugi na produkcji · czas ticket → merge · koszt feature'a.

[18:30–20:30] Cztery rzeczy, których nie widać na poziomie jednego agenta. 01: kod przestaje być limitem. Limitem jest to, ile specu zespół zatwierdzi i ile PR-ów przeczyta. Dlatego bramki muszą być mniej liczne, ale mocniejsze. 02: jeden gigantyczny agent, który pisze i sam siebie reviewuje, zawsze powie „looks good”. Rozdziel role i konteksty. 03: kiedy agent robi ten sam błąd po raz trzeci, nie poprawiasz PR-a — poprawiasz fabrykę: skill, regułę, checklistę. 04: fabrykę się mierzy jak linię produkcyjną. Jeśli nie wiesz, ile PR-ów wraca do poprawek, nie wiesz, czy fabryka działa. [Tu najlepiej pasuje twój własny przykład / liczby z projektu.]

[~2 min] Jak to wygląda w praktyce? Najprostsza fabryka, jaką można postawić jutro: GitHub jako źródło prawdy. Issue to spec — PO i dev dopracowują go w issue. Kiedy człowiek nada label spec-ready, to jest bramka: GitHub Action odpala agenta-implementera, który pisze kod z testami i otwiera PR. Otwarcie PR to kolejne zdarzenie — odpala się reviewer, który sprawdza kod względem specu z issue, nie względem własnych założeń. Label ready-for-qa — agent QA puszcza e2e, robi screenshoty i wrzuca raport. Merge zawsze robi człowiek. Nie ma tu żadnej magii: zdarzenia, labele i joby, które już znacie. Na dole inne modele: plugin zespołowy, gdzie dev sam wywołuje /implement — najbezpieczniejszy pierwszy krok. Chat-ops — PO pisze w Slacku, agent zakłada issue, emoji to akceptacja. Agenci z crona do utrzymania. Pętla z produkcji — alert z Sentry tworzy issue i PR z fixem. Albo własny orkiestrator z kolejką zadań. Granica to wyobraźnia, ale wzorzec jest zawsze ten sam: zdarzenie → agent → bramka.
