02 · Spec-driven development

Przykład: POST /payments

JIRA · PAY-123

Add endpoint allowing a user to pay an invoice.

Priority: High · Estimate: 1 SP 🙂

agent · payments.ts// 🤖 agent: "Done! Endpoint ready ✅" router.post('/payments', async (req, res) => { const invoice = await db.invoices.find(req.body.invoiceId); const payment = await db.payments.create({ invoiceId: invoice.id, amount: req.body.amount, }); res.status(201).json(payment); });
no idempotency key concurrent payments? invoice already paid? no event emitted what if it fails?

Kod jest sensowny. Problem w tym, że nikt nie wie, czy jest poprawny.

[7:30–9:00] To jest nasz przykład na resztę prezentacji: PAY-123.

Typowy ticket — jedno zdanie, estymata 1 SP. Agent generuje endpoint i melduje „Done ✅”. Kod wygląda sensownie.

Stemple wpadają same, po kolei. Skomentuj każdy:

• no idempotency key — klient zrobi retry i zapłaci dwa razy.
• concurrent payments — dwie płatności naraz na tę samą fakturę.
• invoice already paid — nic nie blokuje płacenia opłaconej faktury.
• no event emitted — reszta systemu nie wie, że była płatność.
• what if it fails — co retryować, co zwrócić klientowi?

Agent nie zgadł, bo NIKT mu tego nie powiedział. To nie jest problem modelu — to problem wejścia.

02 · Spec-driven development

Co to właściwie jest spec?

Spec ≠ 40-stronicowy Word

Spec jest wystarczająco konkretny, żeby inny developer albo agent zaimplementował feature bez zadawania 20 pytań.

specs/create-payment.md# Create Payment ## Goal User can create a payment for an existing invoice. ## API POST /payments { invoiceId, amount, clientRequestId } ## Business rules - invoice must exist - invoice cannot already be paid - amount must equal outstanding balance - operation must be idempotent ## Events PaymentCreated · PaymentFailed ## Error cases 404 INVOICE_NOT_FOUND · 409 PAYMENT_ALREADY_EXISTS ## Acceptance criteria - [ ] duplicate clientRequestId → same payment

[9:00–10:15]

Od razu zaznacz: spec to NIE 40-stronicowy dokument w Wordzie. To krótki markdown w repo, obok kodu, z review jak kod.

Test z żółtej karty: czy inny developer albo agent zrobi to bez zadawania 20 pytań?

Pokaż sekcje po prawej: Goal, API, reguły biznesowe, eventy, przypadki błędów, acceptance criteria. Zwróć uwagę na clientRequestId w API — to jest odpowiedź na pierwszy stempel.

02 · Spec-driven development

Dobry spec vs zły prompt

PROMPT

Add payment endpoint.

…i agent zgaduje resztę.

SPEC
POST /payments
Preconditions: invoice exists · status = OPEN
Invariant: payment.amount ≤ invoice.remainingAmount
Idempotency: clientRequestId
Concurrency: optimistic lock on invoice
Side effects: PaymentCreated event
Failure modes: 404 · 409 · 422 → retry only 5xx

AI nie potrzebuje bardziej kreatywnych promptów.
AI potrzebuje mniej zgadywania.

[10:15–11:15]

Lewa strona: to, co dziś zwykle wrzucamy agentowi — „Add payment endpoint.” I agent zgaduje resztę.

Prawa strona: to samo, ale bez niedomówień. Każdy wiersz zamyka jeden stempel z przykładu:

• Preconditions (status OPEN) → opłacona faktura.
• Idempotency (clientRequestId) → podwójna płatność.
• Concurrency (optimistic lock) → równoległe płatności.
• Side effects (PaymentCreated) → brak eventu.
• Failure modes → co gdy się wywali.

Puenta z żółtej karty: AI nie potrzebuje bardziej kreatywnych promptów. Potrzebuje mniej zgadywania. Każda luka w specu to miejsce, w którym agent zgaduje — i zgaduje pewnie siebie.

Problem — ticket albo pomysł. Z niego powstaje SPEC i tu jest pierwsza bramka: człowiek zatwierdza, CO budujemy, zanim powstanie linijka kodu. Błąd złapany tutaj kosztuje minuty, a nie dni.

Kiedy SDD boli

Spec-waterfall

Tydzień pisania specu, zanim ktokolwiek zobaczy działający kod.

Mały spec per feature, iteracyjnie. Prototyp też może być inputem.

Spec drift

Kod się zmienia, spec nie. Po miesiącu spec kłamie.

Zmiana specu w tym samym PR co kod. Review sprawdza oba.

Spec na wszystko

Spec dla literówki w labelu. Ceremonia zamiast wartości.

Spec tam, gdzie są reguły biznesowe albo ryzyko.

Tyle specu, ile ryzyka.

[13:45–15:00] Żeby to nie zabrzmiało jak religia — trzy zarzuty, które słyszę, i wszystkie są zasadne.

Spec-waterfall: „to waterfall od nowa”. Tak — jeśli przez tydzień piszesz spec, zanim ktoś zobaczy działający kod. Rozwiązanie: mały spec per feature, iteracyjnie. Prototyp też może być inputem.

Spec drift: „spec się rozjedzie z kodem”. Tak — jeśli żyje poza PR-em. Spec zmieniamy w tym samym PR co kod, a review sprawdza oba.

Spec na wszystko: literówka w labelu nie potrzebuje specu. Płatności — tak. Spec tam, gdzie są reguły biznesowe albo ryzyko.

Zasada: tyle specu, ile ryzyka.

→ Przejście: „To była jedna funkcja. A co, jeśli takich PAY-123 mamy pięćdziesiąt naraz?”

[15:00–16:15] Trzy poziomy pracy z AI.

LVL 1, asystent: ChatGPT, Claude, Copilot w IDE. Ty prowadzisz cały proces, AI podpowiada.

LVL 2, agent: dajesz mu całe zadanie. Sam czyta repo, zmienia kod, puszcza testy, poprawia błędy i otwiera PR. Tu jest dziś większość zespołów, które na serio używają AI.

LVL 3, fabryka: ticket przechodzi przez wyspecjalizowanych agentów — spec, architekt, backend i frontend równolegle, testy, review — a na końcu człowiek zatwierdza. Developer nie pisze już kodu, tylko projektuje system, który go dostarcza.

Ważne: AI Factory to workflow, nie model. Modele będą się zmieniać, workflow zostaje.

03 · AI Factory

Co się zmienia przy skali?

01

Wąskim gardłem jest człowiek

Agenci produkują więcej PR-ów, niż zespół jest w stanie przeczytać. Limitem są spec i review — nie kod.

02

Separacja ról

Kto implementuje, ten nie reviewuje. Osobny agent, osobny kontekst — review względem specu, nie własnych założeń.

03

Fabryka to też kod

Prompty, skille, CLAUDE.md, checklisty — w repo, wersjonowane, z review. Naprawiasz fabrykę, nie każdy PR.

04

Mierzysz linię produkcyjną

% PR-ów bez poprawek · rework · bugi na produkcji · czas ticket → merge · koszt feature'a.

[16:15–18:00] Cztery rzeczy, których nie widać, dopóki pracujesz z jednym agentem.

01 — wąskim gardłem jest człowiek. Agenci produkują więcej PR-ów, niż zespół jest w stanie przeczytać. Limitem są spec i review, nie kod. Dlatego bramki mają być nieliczne, ale mocne.

02 — separacja ról. Agent, który pisze kod i sam go reviewuje, zawsze powie „looks good”. Reviewer to osobny agent z osobnym kontekstem i sprawdza względem specu.

03 — fabryka to też kod. Prompty, skille, CLAUDE.md, checklisty — w repo, wersjonowane, z review. Kiedy agent trzeci raz robi ten sam błąd, nie poprawiasz PR-a, tylko fabrykę.

04 — mierzysz linię produkcyjną: ile PR-ów przechodzi bez poprawek, ile jest reworku, ile bugów na produkcji, ile trwa droga od ticketu do merge'a i ile kosztuje feature. Jeśli tego nie wiesz, nie wiesz, czy fabryka działa.

[18:00–20:00] Jak to wygląda w praktyce? Najprostsza fabryka, którą można postawić jutro: GitHub jako źródło prawdy, a GitHub Actions reagują na zdarzenia.

Przejdź po górnym pasku: issue to spec — PO i dev dopracowują go w issue. Label spec-ready to bramka: człowiek mówi „spec gotowy” i Action odpala implementera, który pisze kod z testami i otwiera PR. Otwarcie PR to kolejne zdarzenie — startuje reviewer i sprawdza kod względem specu z issue. Label ready-for-qa — agent QA puszcza testy e2e, robi screenshoty i wrzuca raport. Merge zawsze robi człowiek.

Nie ma tu żadnej magii: zdarzenia, labele i joby, które wszyscy znacie.

Dolne karty, krótko, po jednym zdaniu:
• Plugin zespołowy — dev sam wywołuje /implement; najbezpieczniejszy pierwszy krok.
• Chat-ops — PO pisze w Slacku, agent zakłada issue, emoji to akceptacja.
• Agenci cykliczni — cron do utrzymania: zależności, flaky testy, nocne QA.
• Pętla z produkcji — alert z Sentry tworzy issue i PR z poprawką.
• Własny orkiestrator — agenci biorą zadania z kolejki.

Ostatnia karta: granica to wyobraźnia, ale wzorzec jest zawsze ten sam — zdarzenie, agent, bramka.

Q&A — możliwe pytania i krótkie odpowiedzi:

• „Jakie narzędzia?” — Claude Code, Codex, Cursor; do specu: Spec Kit, Kiro, BMAD albo własne komendy. Narzędzie jest wtórne, nawyk pisania specu jest kluczowy.
• „A juniorzy? Jak mają się uczyć?” — Czytając i weryfikując kod agenta, pisząc specy i testy. To otwarty problem — warto o nim rozmawiać w zespole.
• „Ile to kosztuje?” — Tokeny są tanie w porównaniu z godziną developera. Drogie są rework i bugi na produkcji, dlatego mierzymy linię.
• „Czy to nie waterfall?” — Nie, jeśli spec jest mały i iteracyjny. Tyle specu, ile ryzyka.
• „Bezpieczeństwo?” — Agent ma uprawnienia jak junior: brak dostępu do produkcji, sekrety poza repo, merge zawsze robi człowiek.
