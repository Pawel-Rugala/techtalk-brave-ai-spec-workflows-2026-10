02 · Spec-driven development

Przykład: POST /payments

JIRA · PAY-123

Add endpoint allowing a user to pay an invoice.

Priority: High · Estimate: 1 SP 🙂

agent · payments.ts// 🤖 agent: "Done! Endpoint ready ✅" router.post('/payments', async (req, res) => { const invoice = await db.invoices.find(req.body.invoiceId); const payment = await db.payments.create({ invoiceId: invoice.id, amount: req.body.amount, }); res.status(201).json(payment); });
no idempotency key concurrent payments? invoice already paid? no event emitted what if it fails?

Kod jest sensowny. Problem w tym, że nikt nie wie, czy jest poprawny.

[7:00–9:00] Nasz przykład na całą prezentację. Typowy ticket, agent coś generuje — wygląda OK. Stemple wpadają jeden po drugim: brak klucza idempotencji (retry = podwójna płatność), co przy dwóch równoległych płatnościach, co z już opłaconą fakturą, brak eventu PaymentCreated, co gdy coś się wywali w połowie. Agent nie zgadł, bo NIKT mu nie powiedział. To nie jest problem modelu.
02 · Spec-driven development

Co to właściwie jest spec?

Spec ≠ 40-stronicowy Word

Spec jest wystarczająco konkretny, żeby inny developer albo agent zaimplementował feature bez zadawania 20 pytań.

specs/create-payment.md# Create Payment ## Goal User can create a payment for an existing invoice. ## API POST /payments { invoiceId, amount, clientRequestId } ## Business rules - invoice must exist - invoice cannot already be paid - amount must equal outstanding balance - operation must be idempotent ## Events PaymentCreated · PaymentFailed ## Error cases 404 INVOICE_NOT_FOUND · 409 PAYMENT_ALREADY_EXISTS ## Acceptance criteria - [ ] duplicate clientRequestId → same payment
[9:00–11:00] Od razu zaznacz: spec to NIE 40 stron w Wordzie. To markdown w repo, obok kodu. Test: czy inny developer albo agent zaimplementuje to bez zadawania 20 pytań? Pokaż sekcje: goal, API, reguły biznesowe, eventy, błędy, acceptance criteria.
02 · Spec-driven development

Dobry spec vs zły prompt

PROMPT

Add payment endpoint.

…i agent zgaduje resztę.

SPEC
POST /payments
Preconditions: invoice exists · status = OPEN
Invariant: payment.amount ≤ invoice.remainingAmount
Idempotency: clientRequestId
Concurrency: optimistic lock on invoice
Side effects: PaymentCreated event
Failure modes: 404 · 409 · 422 → retry only 5xx

AI nie potrzebuje bardziej kreatywnych promptów.
AI potrzebuje mniej zgadywania.

[11:00–12:30] Lewa strona — to, co dziś wrzucamy agentowi. Prawa — to samo, ale bez niedomówień. Każdy wiersz spec zamyka jeden stempel z poprzedniego przykładu. Puenta: nie potrzebujemy lepszych promptów, potrzebujemy mniej zgadywania. Każda luka w specu to miejsce, w którym agent zgaduje — i zgaduje pewnie siebie.

[14:00–15:30] Tak wygląda spec-driven workflow. Problem → spec → plan → agenci → review → PR. Ważne są dwie bramki, gdzie decyduje człowiek. Pierwsza: SPEC. Zanim powstanie jakakolwiek linijka kodu, człowiek zatwierdza, CO budujemy. Błąd złapany tu kosztuje minuty, a nie dni. Druga: PR. Na końcu człowiek decyduje, czy to wchodzi. Pomiędzy bramkami jest build loop: agent sam robi plan, rozbija go na taski, koduje, pisze testy, robi review i poprawia — w pętli, aż spec jest spełniony. Nikt nie prowadzi go za rękę krok po kroku. Spec to szyna, po której jedzie cały proces — pętla sprawdza się względem specu, nie względem własnego zdania. ▸ Człowiek nie wykonuje każdego kroku. Człowiek pilnuje bramek. 04 · Co może się zepsuć

Anti-patterns

#1

Prompt-driven development

"make it work""fix tests""implement JIRA-123"
…bez kontekstu.

#2

Giant autonomous agent

Jeden agent: requirements, architektura, implementacja, review, testy, deploy. Brzmi fajnie — zero separacji odpowiedzialności.

#3

AI reviewuje własne założenia

Agent implementuje według swojej interpretacji i sam to reviewuje: "Looks good ✅"
Review względem spec, nie względem kodu.

#4

Brak deterministycznej walidacji

Jedyna kontrola: "Claude says it looks good"
Potrzebujesz: compiler · types · tests · schemas · contracts · linters · security checks.

[23:30–24:30] Żeby nie brzmiało jak AI-utopia. Cztery rzeczy, które widzę najczęściej. Szczególnie #3: agent reviewujący własne założenia zawsze powie „looks good”.
